# RP Optional Play Modes Plan · 跑团 / 安科 / 安价 / 骰子系统规划

本文档规划项目中的可选玩法系统：跑团、安科、安价、骰子。它们不是默认 RP 的替代品，而是可嵌入 Actor / Director 两种模式的增强模块。

---

## 1. 目标

新增一组可选玩法能力，使 RP 可以在需要时进入更强规则感、随机性和多人共创感的模式：

- **跑团**：类似 TRPG / 桌面角色扮演，强调场景回合、行动声明、判定、结算、记录。
- **安科**：通过骰子或随机表决定剧情分支、遭遇、NPC 反应、事件强度、暗线推进。
- **安价**：由用户提供候选方向、行动、台词大意、事件提案或选项，agent 负责筛选、转译和落地。
- **骰子**：核心采用 WoD 风格 d10 骰池系统；d100 / 权重表用于安科、事件表和辅助随机。

核心目标不是“随机覆盖叙事”，而是让随机、投票、判定都服从角色内生推演、世界规则、感知边界、能力边界和 OOC 检查。

---

## 2. 与 Actor / Director 模式的关系

跑团、安科、安价不是第三种主模式，而是可叠加在原有两种模式上的玩法层。

### 2.1 Actor + 跑团 / 安科 / 安价

Actor 模式下：

- 用户主要控制主角方向、意图、策略、台词大意。
- agent 可以代写主角具体行为和对白，但必须经过角色知识、能力、心理、动机、习惯校验。
- 跑团规则用于判定主角行动是否成功、消耗多少资源、造成什么后果。
- 安科可用于决定外部事件、NPC 反应、随机遭遇、隐藏线索是否出现。
- 安价可让用户提出主角行动候选、剧情方向候选或对话候选，但候选不是绝对裁决。

Actor 模式重点：

- 不把用户意图当最终结果。
- 不把安价当免费改命。
- 不把骰子成功当作越过能力、资源和信息边界的许可。
- 主角不知道的信息不能因为用户知道而进入主角决策。

### 2.2 Director + 跑团 / 安科 / 安价

Director 模式下：

- agent 可以控制所有角色和推进节奏。
- 跑团规则用于给复杂局势提供透明判定、回合结构和后果记录。
- 安科可用于决定场外暗线、NPC 阵营选择、势力反应、事件升级或降温。
- 安价可用于让用户参与剧情候选设计、事件池设计、NPC 反应候选设计。

Director 模式重点：

- 扩大控制范围，不取消角色边界。
- NPC 不能因为叙事层知道真相而直接知道真相。
- 每个 NPC 的判断必须基于其感知范围、注意力、能力、证据链、心理和动机。
- 随机表结果必须经过合理性筛选，不能生成 OOC 或世界规则不允许的结果。

### 2.3 组合形态

| 组合 | 用途 |
|------|------|
| Actor + 跑团 | 用户给主角方向，agent 做判定、结算、NPC 反应 |
| Actor + 安科 | 主角行为由用户方向决定，外部变量由随机表推动 |
| Actor + 安价 | 用户给候选行动/台词，agent 校验后转译为角色可行行为 |
| Director + 跑团 | agent 控全局，但关键冲突透明判定 |
| Director + 安科 | 大局、暗线、NPC 反应用随机表增加不可预期性 |
| Director + 安价 | 用户参与剧情候选设计，agent 做合理性裁定 |
| 跑团 + 安科 + 安价 | 用户提供候选 → 合法性筛选 → 随机/投票决定 → 跑团结算 |

## 3. 基础原则

所有可选玩法都必须遵守现有 RP 核心规则：

1. **角色内生推演优先**：先看角色知道什么、能做什么、想做什么，再决定行为。
2. **用户意图不是裁决**：用户输入是方向和素材，不是自动成功或自动发生。
3. **NPC 不吃上帝视角**：NPC 推断必须有感知、注意、能力、证据链。
4. **感知不是自动雷达**：目标必须在范围内、有对应感知能力、注意力覆盖，才可能被感知。
5. **骰子不突破世界规则**：随机结果不能越过能力、资源、因果和设定限制。
6. **安价不免费改命**：候选可被筛掉、转译、降级或带来代价。
7. **跑团判定不是结果外挂**：成功、失败、大成功、大失败都要按局势合理落地。
8. **后果必须记录**：重要资源、伤势、状态、关系、知识、战斗日志要写入角色卡模块或 memory。

## 4. 跑团系统规划

### 4.1 定位

跑团系统提供结构化流程：行动声明、难度设定、骰子判定、结果解释、状态结算。

它适合：

- 战斗。
- 潜入。
- 调查。
- 社交交涉。
- 逃亡。
- 追踪。
- 仪式。
- 多 NPC 阵营博弈。
- 需要透明风险与代价的关键行动。

### 4.2 基础流程

```text
1. 场景框定
   - 时间、地点、参与者、目标、风险、限制。

2. 行动声明
   - 用户/角色声明意图。
   - agent 将模糊意图转译为角色可能采取的具体行动。

3. 合法性校验
   - 知识、能力、资源、距离、感知、心理、动机、关系、世界规则。

4. 难度设定
   - 基础难度 + 环境修正 + 对手修正 + 准备修正 + 资源修正。

5. 判定
   - 骰子 + 属性 / 技能 / 能力 / 资源 / 优劣势。

6. 结果分级
   - 大成功 / 成功 / 部分成功 / 失败 / 大失败。

7. 叙事落地
   - 把结果转为角色行动、NPC 反应、环境变化。

8. 状态结算
   - 更新资源、伤势、关系、物品、知识、战斗日志。
```

### 4.3 判定维度

建议第一版不绑定单一 TRPG 规则，而使用项目通用判定框架：

| 维度 | 示例 |
|------|------|
| 属性 | 力量、敏捷、耐力、智力、感知、意志、魅力 |
| 技能 | 潜行、交涉、调查、格斗、术式、驾驶、欺骗 |
| 能力 | 魔法、异能、装备、血统、职业特性 |
| 资源 | 体力、魔力、弹药、时间、情报、人脉 |
| 环境 | 黑暗、噪声、遮挡、天气、地形、监控 |
| 对手 | 警戒、感知、抗性、经验、组织支援 |
| 心理 | 恐惧、愤怒、犹豫、专注、疲劳 |

### 4.4 结果分级

| 结果 | 含义 |
|------|------|
| 大成功 | 达成目标，并获得额外优势或减少代价 |
| 成功 | 达成主要目标，付出正常代价 |
| 部分成功 | 达成部分目标，但产生代价、暴露、延迟或新风险 |
| 失败 | 未达成目标，局势恶化或资源损失 |
| 大失败 | 失败并触发严重后果，但不能凭空 OOC 或破坏因果 |

## 5. 安科系统规划

### 5.1 定位

安科用于在合理候选中引入随机性。它决定“在当前条件下哪个合理分支发生”，而不是创造无因果的神迹。

适合：

- NPC 初始反应。
- 随机遭遇。
- 情报是否被发现。
- 暗线推进速度。
- 场外势力反应。
- 战斗变数。
- 天气、路人、突发事件。
- 关系微变化。

### 5.2 安科表生成原则

安科表必须满足：

- 每个选项都符合世界规则。
- 每个选项都符合当前局势。
- 每个选项都不强制 OOC。
- 权重反映常识、准备、能力、资源、动机和风险。
- 极端结果可以存在，但权重低，且需要因果入口。

### 5.3 示例表

```text
NPC 反应表 d100
01-10：强烈拒绝，并提高警惕
11-35：保留态度，要求更多证据
36-65：表面接受，暗中观察
66-85：部分合作，但提出条件
86-95：主动合作，给出额外线索
96-100：意外信任或暴露隐藏动机（需已有伏笔）
```

### 5.4 安科结果落地规则

骰出结果后：

- 先检查是否仍符合角色知识、能力、心理、动机、关系。
- 若不符合，降级到最近的合理结果，或解释为误判、失败、部分发生。
- 不允许为了保留骰子结果而硬圆 OOC。
- 随机结果应创造变化，而不是替代因果。

## 6. 安价系统规划

### 6.1 定位

安价用于接收用户候选、投票、提案和方向，让用户参与剧情构造。

适合：

- 行动方案候选。
- 台词大意候选。
- NPC 反应候选。
- 事件候选。
- 奖励候选。
- 关系推进候选。
- 世界局势分支候选。

### 6.2 处理流程

```text
1. 收集候选
   - 用户给出 1 个或多个方向。

2. 合法性筛选
   - 剔除超出能力、知识、感知、心理、世界规则的候选。

3. 转译
   - 把不完全合格但有价值的候选转成角色可能采取的相近行为。

4. 排序或随机
   - 按角色动机排序，或用骰子/权重表选择。

5. 落地
   - 叙事执行，并结算后果。
```

### 6.3 安价候选状态

| 状态 | 处理 |
|------|------|
| 合格 | 可直接进入选择或判定 |
| 部分合格 | 转译、降级、附加代价 |
| 不合格 | 剔除，并说明在叙事中表现为角色不会/不能这么做 |
| 高风险 | 可执行，但必须给出代价和后续反应 |
| 重大不可逆 | 需要用户明确确认或足够强输入 |

### 6.4 安价限制

不允许安价直接达成：

- NPC 无铺垫爱上主角。
- 敌人无理由投降或送神器。
- 角色无成本突破能力上限。
- 社会/组织系统无反应。
- 角色获得不该知道的信息。
- 用候选跳过核心冲突。

## 7. 骰子系统规划

### 7.1 核心骰制：WoD 风格 d10 骰池

本项目默认跑团判定采用 WoD / 暗黑世界风格的 d10 骰池，而不是 d20 单骰。

基础形式：

```text
骰池 = 属性 + 技能 + 能力修正 + 环境修正 + 资源修正 - 伤势/压力/干扰惩罚
每颗 d10 独立判定是否成功
累计成功数，与 DC 对比，得到成功 / 失败 / 大失败
```

### 7.2 已确认默认规则

| 项 | 默认规则 | 说明 |
|----|----------|------|
| 骰子 | d10 骰池 | 每次掷 N 颗 d10 |
| 成功阈值 | 8+ | 每颗 d10 掷出 8、9、10 计 1 成功 |
| 加骰 / 爆骰 | 默认 10-again | 掷出 10 追加 1 颗 d10，追加骰继续按同规则判定 |
| 加骰强化 | 能力可改为 9-again / 8-again | 最低只能降到 8-again，不再低于 8 |
| 1 点规则 | 1 不抵消成功 | 默认不使用旧 WoD 的 1 抵消成功 |
| 难度 | 使用 DC | DC = 需要达到的成功数 |
| 结果类型 | 只区分成功 / 失败 / 大失败 | 默认不做大成功、部分成功等独立结果级别 |
| 大失败 | 完全 0 成功 | 只有最终总成功数为 0 时才是大失败 |
| 骰子明细 | 默认公开 | 默认显示骰池、骰面、加骰、成功数、DC、结果 |

### 7.3 判定规则

默认判定逻辑：

```text
if successes >= DC: 成功
else if successes === 0: 大失败
else: 失败
```

说明：

- “成功”表示达成声明行动的主要目标。
- “失败”表示未达成主要目标，但不自动触发灾难性后果。
- “大失败”表示完全没有成功，局势明显恶化或付出严重代价。
- 超过 DC 的额外成功可以记录为 margin，但默认不升级为独立“大成功”等级。
- 大失败不能凭空制造 OOC、破坏因果或跳过角色/世界规则；后果必须从当前局势自然推出。

### 7.4 可配置项

第一版实现为“可配置 WoD 风格骰池”，但默认值按上节固定。

- `pool`: 骰池数量。
- `dc`: 需要达到的成功数。
- `targetNumber`: 成功阈值，默认 8。
- `again`: 加骰阈值，默认 10；能力可改为 9 或 8，最低 8。
- `ones`: 默认 `ignore`，即 1 不抵消成功。
- `showDetails`: 默认 true，公开骰子明细。
- `modifiers`: 来自伤势、环境、资源、心理、装备、准备、对手的修正。

### 7.5 d100 / 权重表的定位

`d100`、权重表和普通随机不作为核心跑团判定，而用于：

- 安科事件表。
- NPC 反应表。
- 遭遇强度表。
- 暗线推进表。
- 奖励/线索/风险表。

### 7.6 Seed 策略

随机不可由用户指定 seed，也不提供 replay / 复现接口。

每次调用自动生成即时 seed：

```text
seedTime = 当前本地时间，精确到秒
internalSalt = 运行时一次性随机盐
seedSource = seedTime + internalSalt
```

对外记录可显示秒级时间戳，便于审计“当时何时掷骰”；但不公开内部盐，不提供复现入口。这样满足“即时、不可复现、不可预设”的玩法需求。

### 7.7 项目级独立包

骰子、安科、安价随机能力做成项目级独立包，不做全局包。

推荐路径：

```text
packages/rp-random/
  package.json
  src/
    index.js
    dice-pool.js
    table.js
    anka.js
    ankage.js
    seed.js
    format.js
  bin/
    rp-random.js
  test/
    dice-pool.test.js
    table.test.js
```

包能力：

- `rollPool`：WoD 风格 d10 骰池判定。
- `contestPool`：对抗骰池。
- `rankOutcome`：成功数按 DC 转为成功 / 失败 / 大失败。
- `rollTable`：d100 / 权重表抽取。
- `rollAnka`：安科表抽取。
- `prepareAnkage`：安价候选格式化与状态标记。
- `makeInstantSeed`：秒级即时 seed + 内部盐。
- `formatResult`：输出可读判定结果。

CLI 作为包的一部分：

```text
node packages/rp-random/bin/rp-random.js pool --pool 7 --dc 3
node packages/rp-random/bin/rp-random.js pool --pool 7 --dc 3 --again 8
node packages/rp-random/bin/rp-random.js table data/rp-tables/npc-reactions.json
```

### 7.8 实现语言

用户表示 JS / TypeScript 都可以。第一版建议使用 JS CommonJS 快速实现，理由：

- 当前项目已经存在 CJS 工具脚本。
- 无需先引入 TypeScript 构建链。
- API 稳定后可再迁移 TypeScript。

## 9. 插件 / 包 / 脚本路线评估

### 9.1 项目级独立包

本系统应实现为项目级独立包，而不是全局包。

推荐：

```text
packages/rp-random/
```

定位：

- 只服务当前 RP 项目。
- 可被本项目脚本、未来 Pi 扩展、规则流程共同调用。
- 不发布为全局 npm 包。
- 不污染其他项目。

优点：

- 结构比散落脚本清晰。
- API 稳定后可直接被扩展工具包装。
- 保留项目内快速迭代能力。
- 后续若跨项目复用，再考虑抽成独立发布包。

### 9.2 项目脚本 wrapper

可以保留轻量 wrapper，但核心逻辑不放在 `tools/`。

可选：

```text
tools/rp-random.cjs  # 调用 packages/rp-random 的 CLI wrapper
```

用途：

- 方便命令行调用。
- 兼容现有工具习惯。
- 不承载核心规则逻辑。

### 9.3 Pi 扩展插件

插件作为第二阶段封装。

等 `packages/rp-random` 的 API 稳定后，再新增项目内扩展，例如：

- `rp_roll_pool`
- `rp_roll_table`
- `rp_anka`
- `rp_ankage`

插件只负责参数校验和工具调用；随机核心仍在项目包。

### 9.4 全局包 / 发布包

暂不做。

原因：

- 当前玩法规则仍在项目内演化。
- 不需要跨项目复用。
- 发布包会增加版本、构建、兼容和维护成本。

### 9.5 推荐路线

```text
阶段 1：更新规则与计划文档
阶段 2：实现 packages/rp-random 项目级独立包
阶段 3：加入基础 JSON 随机表与测试
阶段 4：接入 rp-engine / rp-dice / quality-check
阶段 5：按使用频率封装项目内 Pi 扩展插件
阶段 6：如未来多个项目复用，再考虑发布独立包
```

## 12. 待确认问题

已确认：

- 实现形态：项目级独立包，不是全局包。
- 默认随机核心：WoD 风格 d10 骰池系统。
- 成功阈值：固定默认 8+。
- 加骰：默认 10-again；能力可改为 9-again / 8-again，最低 8-again。
- 难度：使用 DC，需要成功数达到 DC 才算成功。
- 结果分级：默认只区分成功 / 失败 / 大失败。
- 大失败：只有最终总成功数完全为 0 时触发。
- 1 点规则：默认不抵消成功。
- 骰子明细：默认公开。
- d100：保留给安科表、事件表、反应表。
- seed：不可由用户指定；使用即时秒级时间 + 内部随机盐；不提供复现接口。
- 实现语言：JS CommonJS 或 TypeScript 都可；第一版建议 JS CommonJS。

剩余实现选择：

1. 第一版是否立即实现 `packages/rp-random/`，并配套最小测试？
2. 是否同时新增基础随机表 `data/rp-tables/npc-reactions.json` 等样例？
3. 是否在第一版就做 Pi 扩展工具包装，还是先只提供包 + CLI？建议先包 + CLI。
